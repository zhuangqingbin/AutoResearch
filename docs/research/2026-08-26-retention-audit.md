## Existing replay tooling + its PIT rules

**The funnel replayer is gone.** `autoresearch/research/replay.py` was deleted 2026-08-21 with the learning-layer retirement — stated at `.claude/skills/scan-market/STAGES.md:138` ("原**漏斗回放器** `research/replay` 已随 2026-08-21 闭环退役删除 —— 它的归因腿读的是 `retro.attribute`") and listed among the deleted offline instruments at `STAGES.md:246`. Confirmed by `ls autoresearch/research/` — no `replay.py`. Its PIT rule survives only as a vestige: `universe.run(weights_path=…)` (`scan/universe.py:305, 312-314`) exists solely so a replayer could inject an as-of weights snapshot, because `weights.json` is calibrated on forward returns — "拿它回放历史 = 用未来的权重预测过去". Nothing calls it with a non-None value today.

**What replay machinery does still exist:**

1. **`autoresearch/news/catalog.py:358-375` — `NewsCatalog.replay(code, decision_cutoff_ts, stage)`.** Real PIT semantics, documented at `catalog.py:28-36`: only observations with `first_seen_ts ≤ cutoff` **and** `available_stage ≤ stage` are visible; `published_ts` is explicitly excluded from filtering ("它是来源陈述"); `snapshot_inferred` rows must not replay before their snapshot time. **But it is not wired into the pipeline** — `scan/prelude.py:411-421` only *reads* it for a coverage/freshness report line, annotated "**只看,不喂决策**". Verified on disk: 8,253 observations, **`scan_run_id` populated on 0 of them**, 5,644 are `snapshot_inferred`. So it cannot currently tell you what a *specific run* saw. Its `raw_artifact_path` column also carries a stale prefix (`context/lake/stock_news_em/…`) that no longer matches the actual lake root `lake/`.
2. **`autoresearch/scan/price_claims.py:640 — `replay(scan_root, days)`.** Re-audits historical cards' price assertions against verified OHLCV. Narrow scope (price claims only), and it reads `scan_root` = **staging**, not the published run dir.
3. **`autoresearch/scan/l4_watch.py:319-334 — `--replay-all`.** Unrelated: re-broadcasts progress events from a cursor.

What it **does not** capture: any content hash of agent defs / skills / playbooks; any dirty-tree signal; any lake manifest; any input lineage. `ArtifactIndex` deliberately writes `"input_hash": None` for every artifact (`artifacts.py:118-119`, comment: "生产者尚未回显 lineage 时必须诚实为空，不能用 contract hash 冒充输入指纹"), and the plan doc lists producer-level `input_hash` as unbuilt future work (`docs/plans/2026-07-28-run-contract-artifact-index-plan.md:1083`). Grep confirms `input_hash` appears in exactly three places in the codebase, all in `artifacts.py`, always `None`.

One design precedent worth reusing: `scan/run_mode.py:19,154` already refuses to read `pinned.jsonc` at report time precisely because "那份配置跑后可能被改" — it reads the frozen `run_contract` snapshot instead. That instinct just hasn't been extended to prompts, slim, or the lake. (Ironically `run_mode.json` itself is not published.)

## Bottom line for 复盘

Given `reports_claude/scan/20260825_2149/` alone, you can reconstruct: the funnel counts and rankings, the exact L3 table the ranker read, its judgments, the exact L4 prompt text dispatched, the intel it gathered, the final cards, and the decision records. You **cannot** reconstruct: the market view it was anchored to, the raw evidence behind the L3 table columns, the slim data every card number came from, the ensemble reviewers' reasoning, the dossier text as-read, the agent rubrics as-configured, the gate-fire verdicts, or the lake values as-of that day. And if the same data day was rescanned, the staging copies of all of the above are already overwritten.
